- **Commission:** Mike, Nov 24, 2026, 4:16 PM CT — when a player finds a chain-locked quest NPC, "it should let the player know what they need to do or what quests they need to do first before this one unlocks." - **What it is:** module #22 of ExcelEMFixes, **quest-chain-clarity** (default ON). When a player clicks an EliteMobs quest NPC and a quest stays locked because its accept permission (the previous quest in its chain) is unmet, the player gets one specific line per locked chain after EliteMobs' own message, e.g. `Locked: finish 'Population Control!' first — King Nemian gives it.` The named quest is the NEXT one the player can actually do (the walk follows accept-permission links to the first quest whose own accept permissions the player already holds); the giver and place come from that quest's own data. Everything is computed from EliteMobs' loaded quest/NPC registries and the player's completion markers read exactly as EliteMobs' own `CustomQuest.hasPermissionForQuest` reads them. No quest, NPC, or place is known by name.
- **Detection route:** EliteMobs' api/ events cover quest accepts/completions/progression but NO event fires on a refusal, so the module listens to the same click EliteMobs does (`PlayerInteractEntityEvent`, main hand, MONITOR, observe-only) and replicates only the accept-permission segment of EliteMobs' check. **Critical:** EliteMobs CANCELS this event for its NPCs, so the listener deliberately does NOT use `ignoreCancelled` — with it, the handler never runs (caught on the rig before filing; documented in the module's class comment).

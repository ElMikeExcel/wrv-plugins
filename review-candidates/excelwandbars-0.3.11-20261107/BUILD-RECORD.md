## The bug (from the investigation, source-convicted)

ExcelMenuJoin's join-time compass check inspects the PRESENTED inventory. A player who logs out with the spell bar open is restored by Magic at the next join with the bar open, so the check cannot see the real compass stored inside the wand → a duplicate compass is handed out, lands in the presented bar (`addItem` is hotbar-first), and is saved into the wand's page contents, where it re-renders at every later open. The 0.3.8 join guard was the backstop but races the restore (checks at 1.5 s / 4 s / 8 s; three candidate defeats, above), and the exit sweep never ran on the restored path because `tryOpen` returns "already open" before its sweep step.

## The ordering finding (why the hook point deviates from the spec's letter)

The task spec said "in TapBarHook, on player quit, close any open bar using the same closeInventory() call stop() uses." Bytecode verification against Magic 11.2.5 (`~/workspace/magic-scratch/downloads/Magic-11.2.5.jar`) showed the literal placement is **inert at Magic's default settings**:

- Magic's `PlayerController.onPlayerQuit` is `@EventHandler(priority = LOWEST)`; at `logout_delay: 0` (Magic's shipped default, `defaults/config.defaults.yml` line 1086) it synchronously deactivates the mage in the quit event itself: `getActiveWand()` → `isInventoryOpen()` → `flagForReactivation()` (which records `restoreOpenWand` from the wand's open state at that instant) → `deactivate()` → save.
- Magic enables before ExcelWandBars (depend), so within LOWEST its handler runs FIRST. Any WandBars `PlayerQuitEvent` handler, at any priority, runs after deactivation — `openWand(p)` returns null and the close silently never happens. The 0.3.10 rig proved the same fact from the other side: after a fired quit event, a direct cleanup restored 0 because "no active wand remains — Magic deactivated it in its own quit handling."

**Remedy — same behavior, same scope, different hook point:** Paper's `PlayerConnectionCloseEvent` (`com.destroystokyo.paper.event.player.PlayerConnectionCloseEvent`), bytecode-verified in the Paper 26.3 server jar to be constructed and `callEvent()`ed synchronously (async=false) from `net.minecraft.network.Connection` teardown for game-profile connections — i.e., BEFORE player removal and BEFORE `PlayerQuitEvent` dispatch, while the mage is still active and the wand still open. The spec's literal placement is ALSO implemented (top of `TapBarHook.onQuit`) as a belt: in a `logout_delay > 0` setup Magic defers deactivation past the quit event, and there the belt is the path that lands. Both call the one shared `TapBarHook.closeBarAtExit(p, why)`.

## The fix

1. **Quit close (B) — `QuitCloseHook` + `TapBarHook.closeBarAtExit` + `core.QuitClosePlan`.** `QuitCloseHook` (own class, registered in its own try/catch in `ExcelWandBars` beside the tapBar block — the house isolation pattern for platform-optional hooks) resolves the player from the connection-close event and calls `closeBarAtExit(p, "connection close")`. The decision is the pure `QuitClosePlan.decide(enabled, usesTapBar, wandPresent, barOpen)` with `enabled` = the existing `join-starts-on-items` switch (the logout close is that policy enforced at the other end of the session — **no new config key**). On CLOSE it calls the same `w.closeInventory()` `stop()` uses (Magic's own close; real items restored), verifies the bar is down, counts `quit-closes` / `blocked`, and logs `Quit close: <name> logged out with the spell bar open (…); items restored (joins start on your items).` With the bar closed at every logout, Magic's restore decision always reads "closed": no join starts on the wand bar, and the blind compass give loses its precondition. The join guard remains as backstop, untouched.
2. **Join sweep (A-lite) — `core.JoinSweepPlan` in `joinGuardCheck`.** The guard's checks at 30/80 ticks keep the existing signature; the 160-tick check now passes `finalCheck = true`. When the verdict is LEAVE and `JoinSweepPlan.shouldSweep(guardEnabled, sweepEnabled, finalCheck, guardLeft, barOpen, alreadySwept)` holds, the guard runs the existing `ExitSweep.run(...)` once (per-join set, cleaned on quit), counts `join-sweeps` / `moved` / `left`, and returns the distinct result word `leave (bar open; join sweep ran)`. This evicts compasses (and any foreign item) baked into saved pages before 0.3.11, on the owner's next join, into the stored (real) inventory — moved, never deleted; CompassGuard's standing tidy then trims to exactly one compass once the bar closes.

Scope held: ExcelMenuJoin untouched; the occupied-slot swap path untouched; no config changes; no new data files (all new state is in-memory).

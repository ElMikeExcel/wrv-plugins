## The bug (verified in `../COOLDOWN-64-INVESTIGATION.md`)

Magic writes each spell icon's stack amount as `ceil(time-to-cast / 1000)` clamped to [1, 99], where time-to-cast is the max of remaining cooldown, charge recharge, and mana wait (`Mage.updateHotbarStatus`, bytecode-verified in Magic 11.2.5). Geyser then flattens any amount to 64 for Bedrock clients. So on Bedrock a 4-minute Familiar cooldown reads "64" for most of its wait, and on Java it pins at 99 — the number cannot tell the truth past ~a minute either way. Mike's screenshot (Nov 3, 9:47 AM CST) showed exactly this: Familiar's egg at 64 with ~3 minutes left.

**Repro (rig, stock 0.3.9):** mend given a 240 s time-to-cast — the icon's name shows nothing about the remaining time (`mend  (Active rank 2 of 5)`) while Magic's own value reads 238,488 ms. Fixture limitation, stated plainly: the fixture does not run Magic's live amount updater for the synthetic player (all amounts stay 1), so the 99/64 pin itself is asserted at formula level — `min(99, ceil(ttc/1000)) == 99` — and stands on the bytecode verification in the investigation file plus Mike's live screenshot.

## The fix — name-tag countdown (`NameTagHook` + `core/CooldownTagPlan`)

While a wand-mode hotbar spell's true time-to-cast (Magic's own `BaseSpell.getTimeToCast()`, the same max-of-three value) exceeds the threshold, the icon's display name is annotated: `Familiar · 3:24` (the spell's own painted name, middle dot, m:ss, seconds ceilinged so the tag never understates). At or below the threshold the name is left alone and Magic's number does the talking; when the spell becomes castable the annotation clears on the next poll.

Mechanics, and why they are stable against Magic's refresh (the task's hard ordering question, settled by bytecode before code):

- `Mage.updateHotbarStatus()` / `BaseSpell.updateItem` never write the display name or lore — only the stack amount and the icon art (material/skull). Names are painted at inventory-build time and by WandBars' own `TapBarHook.applyLore` on open/cast. So there is no per-tick fight: a 10-tick poll appends the suffix to the current name, and after any repaint it simply re-appends.
- The first annotation records the spell's name component verbatim in a PDC marker (`cooldown_name_tag`, Gson-serialized component) plus the spell key (`cooldown_name_spell`). Every refresh re-renders from the **recorded base**, so suffixes can never stack; if the marker's spell key no longer matches the icon's spell, the copy is stale and is restored instead of refreshed.
- The suffix is a separate gray, non-italic text component appended after the spell's own name — Magic's name and lore underneath are never rewritten, and restore puts the recorded base back byte-for-byte (rig-verified: page paint byte-identical after a raw close mid-cooldown).
- The stack amount is never touched (rig-asserted: WandBars writes no amount).
- Platform parity is by construction: the annotation lives in the item's display name, which Java renders natively and Geyser translates for Bedrock the same way it translates every other spell name. (Bedrock rendering itself is a player proof — see below.)

## Save-safety (the 0.3.9 pager-leak discipline, applied in full)

Annotated icons are display copies only. The defenses mirror `PagerHook`'s:

1. **Pre-save sweeps:** `MagicHook.sweepNameTag` runs beside `sweepPager` at all three sweep sites (sneak-flip branch, `flipPage`, `flipListPage`), so any save WandBars itself initiates sees a clean display. Rig: a WandBars flip saved with **no** annotated copy in the page paint, checked in the same tick before the cleanup poll could run (hook summary `sweeps 1`).
2. **Standing cleanup:** every poll (and on join, at +20/+60 ticks after join, and at +1/+10 ticks after inventory close) restores marked items found in the wand's stored inventory, in hotbar page contents, in the real inventory while the bar is closed, and on the cursor. Restoration is in place — the recorded base name is put back; nothing is ever deleted. While the bar is open, all pages **except the current one** are restored (the current page is render/sweep-owned); copies Magic's own page cycles save into background pages are therefore collected within one poll. Rig: after a raw Magic close mid-cooldown, the page paint is clean, the real and stored inventories are clean, and the page paint is **byte-identical** to its pre-close serialization.
3. **Quit/join:** the quit handler (LOWEST priority) splits its steps (display sweep / standing cleanup / explicit restore of every hotbar page) into separate guards so one failing step cannot skip the others; join schedules cleanup passes. Rig: at the quit moment the real inventory holds no annotated copy; after the join event and a close, real inventory and page paint are clean.
4. **Persistence shape (bytecode):** a wand's saved state is its spell map plus properties — painted page stacks are never serialized — and for spell items `saveInventory` records only the spell key. An annotated name therefore has no path to disk through the wand at all; the in-memory page paint is the only residue vector, and it is covered by (2).

**One documented observation, not a leak (rig boot16 diagnostic):** at a quit event, Magic's own quit handling (registered earlier, same priority) saves the open inventory and deactivates the wand before WandBars' handler can reach that wand's page paint; a direct cleanup call at that instant restores 0 because there is no active wand left. The copies Magic saved sit only in that deactivated wand object's in-memory paint — never persisted (spell-map persistence, above), rebuilt from the map at the next activation, and the probe's post-join check reads **the same wand object** clean. Everything that is persisted or displayed — real inventory, stored inventory, spell map — is clean in every ordering.

Fail-soft: any error while handling a player disables the feature for that player for the session, restores their display, and logs one warning — the same posture as the pager hook.

## What is NOT proven here

- **The live amount pin (99 Java / 64 Bedrock) is not rig-reproducible** — the fixture never runs Magic's amount updater for the synthetic player. It stands on bytecode + Mike's live screenshot.
- **No true relog:** quit/join are exercised by firing real `PlayerQuitEvent`/`PlayerJoinEvent` through the plugin manager on a still-connected synthetic player, not by an actual disconnect/reconnect.
- **Bedrock rendering** of the annotated name is by construction (same display-name channel as every spell name) — Mike's in-game proof is the decider, listed in the MANIFEST entry.
- Player proofs owed after install are listed in the MANIFEST entry (Mike on Bedrock: Familiar name tag counts down from ~4:00 while the number sits at 64, clears at expiry; Jester on Java: same on a >99 s cooldown).
